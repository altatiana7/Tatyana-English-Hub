# Единая база Supabase

Это второй шаг из трёх: сначала ограничитель Катерины, потом база, и только
после проверки — перенос учеников. Здесь описано, как поднять базу и убедиться,
что чужие данные в ней не видны.

**Что остаётся как есть:** адреса уроков и домашних заданий не меняются.
Страницы уроков, сайты учеников, тренажёры — всё лежит там же, где лежало.
База хранит только планнер: учеников, занятия, оплаты, домашку и ответы.

---

## Что лежит в репозитории

| Файл | Что делает |
|---|---|
| `supabase/schema.sql` | 7 таблиц, вьюха долгов, триггеры. Создаёт структуру |
| `supabase/policies.sql` | правила доступа (RLS): кто что видит и может менять |
| `supabase/tests/rls-smoke.sql` | 23 проверки доступа; выполняется в транзакции и **откатывается** |
| `tools/planner-to-supabase.mjs` | превращает резервную копию планнера в SQL для импорта |

Файлы проверены на локальном Postgres с имитацией окружения Supabase:
схема и политики применяются без ошибок, все 23 проверки доступа проходят,
импорт данных считается верно. **На настоящем Supabase ещё не запускались** —
это первый шаг в инструкции ниже.

---

## Шаг 1. Создать проект

1. Зайдите на [supabase.com](https://supabase.com) и войдите (можно через GitHub).
2. **New project**. Название — например `tatyana-hub`. Пароль базы данных
   сгенерируйте и сохраните в менеджере паролей: он понадобится, только если
   вы будете подключаться к базе напрямую, но терять его нельзя.
3. Регион — **Frankfurt** (ближе всего к Норвегии, отклик меньше).
4. Дождитесь, пока проект создастся (1–2 минуты).

Бесплатный тариф: 500 МБ базы, этого хватит с большим запасом — планнер
весит килобайты. Один нюанс: бесплатный проект **засыпает после недели без
обращений**. Просыпается сам при первом запросе, данные не теряются, но первый
заход может занять несколько секунд. Если это будет мешать — на платном тарифе
этого нет.

## Шаг 2. Создать таблицы и правила

В проекте откройте **SQL Editor** и выполните два файла **по очереди**,
целиком, каждый в отдельном запросе:

1. содержимое `supabase/schema.sql` → **Run**;
2. содержимое `supabase/policies.sql` → **Run**.

Порядок важен: политики ссылаются на таблицы. Оба файла можно выполнять
повторно — они не ломаются от второго запуска.

В конце второго файла должно появиться сообщение `RLS: базовые политики
на месте`. Если появилось — структура готова.

## Шаг 3. Завести аккаунт учителя

Ученики входят по почте и паролю, учитель — так же, только с пометкой в профиле.

1. **Authentication → Users → Add user**. Введите свою почту и пароль,
   включите **Auto Confirm User** (иначе письмо придётся подтверждать).
2. В **SQL Editor** выполните, подставив свою почту:

```sql
update public.profiles
set role = 'teacher'
where lower(email) = lower('ваша-почта@example.com');

select email, role from public.profiles;   -- должно быть teacher
```

Эта строчка — единственное место, где выдаётся роль учителя. Из браузера
сделать это нельзя: право на колонку `role` никому не выдано, а на всякий
случай стоит ещё и триггер, который отказывает в смене роли.

Проверка этого была не лишней: в первой версии политик ученик мог сам себе
выполнить `update profiles set role='teacher'` и получить доступ ко всему.
Теперь оба теста на это есть в `rls-smoke.sql` и проходят.

## Шаг 4. Взять ключи

**Project Settings → API**:

| Ключ | Куда | Почему |
|---|---|---|
| `Project URL` | в планнер | адрес базы |
| `anon public` | в планнер | публичный ключ, его видят все — так и задумано |
| `service_role` | **никуда** | обходит все правила доступа |

`anon`-ключ не секрет: защита держится на правилах (RLS), а не на ключе.
Ученик с этим ключом видит ровно то, что разрешено политиками — это и
проверяют тесты.

`service_role` не вставляйте ни в планнер, ни в страницы, ни в чат. Кто его
получит, увидит и изменит **всё**: имена, оплаты, ответы всех учеников.
Цена ошибки — полная потеря приватности без единого следа в логах.

## Шаг 5. Проверить правила на своём проекте

Пока в базе нет настоящих данных, прогоните `supabase/tests/rls-smoke.sql`
в SQL Editor целиком. Скрипт создаёт тестовых учеников внутри транзакции,
проверяет доступ и делает `rollback` — в базе после него ничего не остаётся.

Ожидаемый результат — 23 строки `ok:` и в конце
`Все проверки пройдены. Изменения откачены.` Если появилась хоть одна
ошибка — дальше не идите, пришлите мне текст ошибки.

## Шаг 6. Перенести данные из планнера

1. Откройте планнер, нажмите **Копии…** (или возьмите самый свежий
   `planner-backup-ГГГГ-ММ-ДД.json` из папки планнера).
2. В командной строке на компьютере, где лежит проект:

```
node tools/planner-to-supabase.mjs planner-backup-2026-10-31.json > supabase/import.sql
```

3. Откройте `supabase/import.sql` и посмотрите глазами: имена, суммы за месяц,
   фактические оплаты. Файл читаемый, ничего не зашифровано.
4. Выполните его в SQL Editor.
5. Проверьте итоги:

```sql
select s.name, d.period, d.planned, d.paid, d.balance
from public.student_debts d
join public.students s on s.id = d.student_id
order by s.name, d.period;
```

`balance` — сколько осталось доплатить. Сверьте с тем, что показывает планнер.
Если числа разошлись — не правьте руками, скажите мне: значит, в исходном
файле данные лежат иначе, чем я предполагал.

Что важно знать про импорт:

* повторить его можно сколько угодно — дубликатов не будет, записи обновятся
  по тем же идентификаторам;
* если в файле есть и суммы по месяцам, и старый список платежей, скрипт берёт
  **один** источник и предупреждает об этом — иначе долг задвоится (я на это
  наткнулся на тестовых данных и поправил);
* `import.sql` содержит имена и суммы, поэтому он в `.gitignore` и в
  репозиторий не попадает. Храните его как резервную копию, но не выкладывайте.

## Шаг 7. Подключить планнер (ещё не сделано)

Сейчас планнер по-прежнему работает только с файлом на компьютере: облачная
синхронизация в нём намеренно отключена. Переключать его на базу будем
отдельным шагом — после того, как вы посмотрите на данные в Supabase и
скажете, что всё верно.

Порядок, который вы задали, соблюдается: сначала база и проверка, потом
ученики. Ни одна страница уроков и домашних заданий на этом шаге не меняется.

---

## Кто что видит

| Кто | Ученики | Занятия | Оплаты | Домашка | Ответы |
|---|---|---|---|---|---|
| Без входа (случайный человек) | нет | нет | нет | нет | может отправить ответ, только зная личный ключ задания |
| Ученик | только себя | только свои | нет | только свои | только свои |
| Учитель | всех | все | все | все | все, может ставить оценку |

Дополнительно: личный ключ задания (`submit_token`) ученик не видит даже в
своей строке — колонка закрыта отдельным грантом. Отправка ответа с публичной
страницы ограничена 10 отправками в час на одно задание, чтобы ключ нельзя
было подобрать перебором.
