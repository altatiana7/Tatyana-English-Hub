# Вынос личных данных из публичного сайта

Решение владельца: **интерактивные уроки остаются на GitHub Pages и открываются
по ссылке**, а журнал успеваемости, персональные данные и оплаты уезжают в
систему с авторизацией.

Документ описывает, что именно нужно вынести, куда и в каком порядке, чтобы
действующие уроки не пострадали ни на одном шаге.

---

а не на сервере.

## 2. Границы: что публично, что приватно

| Остаётся на GitHub Pages (открывается по ссылке) | Переезжает в систему с авторизацией |
|---|---|
| Все уроки и тренажёры (`ege-*`, `spotlight-*`, `go-getter-*`) | Планнер: расписание, ученики, уровни |
| Домашки учеников (`*-homework/`) | Оплаты: тарифы, фактические платежи, долги |
| Личные хабы учеников (`*-english-hub/`) | Заметки о занятиях, история уроков |
| Озвучка карточек, медиа | Журнал успеваемости (Teaching Progress, PR #3) |

Домашки остаются публичными осознанно: ученик должен открыть их по ссылке без
пароля. Персональных данных там нет — только упражнения.

## 3. Почему нельзя просто «поставить пароль на папку»

GitHub Pages не умеет ограничивать доступ по путям. А главное — **репозиторий
публичный**, поэтому любой пароль на страницу бессмысленен: исходники и данные
всё равно лежат в открытом репозитории.

Значит, приватная часть должна одновременно:

1. жить в **закрытом** репозитории или вообще без него (данные в базе);
2. отдаваться с сервера, который умеет авторизацию;
3. хранить данные **на сервере**, а не в `localStorage` браузера — иначе журнал
   останется привязанным к одному устройству и не будет резервной копией.

## 4. Целевая архитектура

```
GitHub Pages (публичный репозиторий)          Cloudflare Pages (закрытый проект)
┌──────────────────────────────┐              ┌────────────────────────────────┐
│ index.html                   │   ссылка     │ journal.<домен>                │
│ уроки, тренажёры, домашки    │ ───────────► │ Cloudflare Access (вход по     │
│ noindex + robots.txt         │              │ коду на e-mail)                │
└──────────────────────────────┘              │  ├─ расписание                 │
                                              │  ├─ оплаты                     │
                                              │  └─ журнал прогресса           │
                                              │ D1 (SQL) — данные на сервере   │
                                              └────────────────────────────────┘
```

Почему Cloudflare:

* **бесплатно**: Pages, Access (до 50 пользователей), D1 в свободном тарифе;
* Access даёт вход по одноразовому коду на e-mail — без паролей, которые надо
  помнить и хранить, и без своего сервера;
* закрытый репозиторий поддерживается бесплатно (у GitHub Pages приватные
  репозитории требуют платного тарифа);
* если позже понадобится — легко добавить второго учителя или родителя с
  доступом только к своему ребёнку.

Альтернативы, если Cloudflare не подходит:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Supabase** + любой статический хостинг | готовая авторизация и Postgres, удобный экспорт | надо писать клиент целиком, чуть больше кода |
| **Vercel** + NextAuth | привычный стек | бесплатный тариф только для некоммерческого использования |
| **Свой сервер** (VPS) | полный контроль | обслуживание, бэкапы, обновления — на вас |

## 5. Порядок переезда (ни один шаг не ломает уроки)

Шаги 1–4 можно делать в любом темпе, уроки в это время работают как обычно.

**Шаг 1. Подготовка (30 минут, без риска).**
Создать аккаунт Cloudflare, новый **приватный** репозиторий `journal` и проект
Cloudflare Pages. Публичный репозиторий не трогаем вообще.

**Шаг 2. Перенос планнера как есть.**
Скопировать `teacher-calendar/planner-v2.html` в новый репозиторий, включить
Cloudflare Access (политика: только ваш e-mail). Данные пока остаются в
`localStorage` — журнал работает ровно как сейчас, но уже за логином, и имена
учеников исчезают из публичного кода.

**Шаг 3. Проверка на себе (неделя).**
Пользуетесь новым адресом как обычно. Старый планнер на GitHub Pages ещё
жив — это страховка. Если что-то не так, просто возвращаетесь на старый.

**Шаг 4. Данные на сервер (основная работа).**
Добавить в Cloudflare D1 таблицы `students`, `lessons`, `payments`, `notes`
и экран входа. Планнер начинает читать и писать в базу вместо `localStorage`.
Обязательно: кнопка «экспорт в JSON» и ежедневный бэкап D1
(`wrangler d1 export`) — журнал успеваемости нельзя хранить в одном месте.

**Шаг 5. Уборка публичной части (только после шага 3).**
Удалить `teacher-calendar/` из публичного репозитория;\
в `index.html` и `my-hub.html` заменить ссылку на новый адрес
(ссылка остаётся видимой — страница за ней защищена Access).\
Из `planner-v2.html` убрать `DEFAULT_STUDENTS` с реальными именами.

**Шаг 6. Обнулить историю (по желанию).**
Имена уже попали в историю git публичного репозитория. Полная чистка
(`git filter-repo`) перезапишет все коммиты и потребует force-push — делать
только осознанно и после бэкапа. Для одноимённых папок учеников это всё равно
не даст эффекта, поэтому шаг необязательный.

## 6. Что можно сделать прямо сейчас, до переезда

Три дешёвые меры, которые снижают риск немедленно и ничего не ломают:

1. Убрать реальные имена из `DEFAULT_STUDENTS` в публичном планнере — они
   нужны только при первом открытии на новом устройстве, дальше берутся из
   `localStorage`. Замена на «Ученик 1…6» убирает имена из кода.
2. Не публиковать новые платёжные данные в репозитории — они и так в браузере,
   достаточно не переносить их в HTML.
3. Оставить `noindex` и `robots.txt` (уже сделано в PR #8) — это убирает
   страницы из поиска, но не отменяет шагов выше.

## 7. Что нужно от владельца

* аккаунт Cloudflare (бесплатный) и подтверждение домена или поддомена
  `*.pages.dev`;
* e-mail для политики доступа Access;
* решение по шагу 6.1 (обезличить имена в публичном планнере сейчас или после
  переезда).

После этого можно писать саму систему: схему базы, вход, перенос данных из
`localStorage` и экспорт.
